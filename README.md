# BlitzSpirit

The source for the BlitzSpirit shop at https://blitz.getbrian.xyz: a British heritage apparel store (t-shirts and caps). It is a static Astro site with a browser-side cart, Stripe Checkout for payment, and Printful for fulfilment.

This repo holds both the source and the built site. Read "How a change goes live" before you edit anything at the repo root.

## Layout

| Path | What it is |
|---|---|
| `standalone/` | The shop's Astro source. This is where you make changes. See [`standalone/README.md`](standalone/README.md). |
| Repo root (`index.html`, `_astro/`, `products/`, `collections/`, `edit/`, `social/`, and so on) | The built shop. Generated by CI and committed. Do not edit by hand. |
| `.published` | Manifest of the entries in the repo root that `tools/publish.mjs` generated. Only entries listed here are ever replaced or removed. |
| `api/` | Vercel serverless functions (CommonJS, no dependencies). Listed below. |
| `tools/` | Node scripts run by CI: `publish.mjs`, `check-edit-ids.mjs`, `test-order.mjs`, `test-content.mjs`, `test-printful.mjs`. |
| `old/` | The original static site, kept for reference. `vercel.json` redirects its old URLs (for example `/about.html`) into `/old/`. |
| `shopify-theme/` | The Liquid theme the shop was ported from. Excluded from the Vercel deployment by `.vercelignore`. |
| `docs/` | Design system, handover notes, deployment notes and other background. Some of it predates the current setup; see the note under "How a change goes live". |
| `vercel.json` | Redirects only. |
| `.github/workflows/build-shop.yml` | The "Build the shop" GitHub Action. |

There is no `package.json` at the repo root. Dependencies live in `standalone/package.json`, and the scripts in `tools/` use only Node built-ins.

### Serverless functions in `api/`

One line each, from the header comment of each file. Files starting with an underscore are shared modules, not routes.

| File | What it does |
|---|---|
| `checkout.js` | `POST /api/checkout`. Creates a Stripe Checkout Session from variant ids and quantities. Prices are re-read from the committed catalogue, never from the request. |
| `stripe-webhook.js` | `POST /api/stripe-webhook`. Turns a paid Stripe Checkout into a Printful order. Stripe test-mode payments are ignored unless `ALLOW_TEST_ORDERS` is `true`. |
| `newsletter.js` | `POST /api/newsletter`. Adds an email address to a Resend audience. Returns 501 if Resend is not configured. |
| `edit.js` | Save endpoint for the inline copy editor at `/edit`. Rewrites one known string field in the committed JSON under `standalone/src/data/` and commits it through the GitHub API. |
| `social.js` | Reads and writes the copy-dossier overrides behind `/social`, stored in a Supabase project. |
| `admin.js` | Password-gated serverless proxy to Supabase for the feedback admin. Predates the current shop. |
| `feedback.js` | `POST` endpoint that stores feedback comments in Supabase. It has no header comment; this line comes from reading the handler. |
| `_order.js` | Turns a bag of variant ids into priced Stripe line items. Shared by `checkout.js` and `tools/test-order.mjs`. |
| `_printful.js` | Turns a paid Stripe Checkout Session into a Printful order. Shared by `stripe-webhook.js` and `tools/test-printful.mjs`. |
| `_content.js` | Resolves the editor's field addresses (for example `pages/index:hero.settings.heading`) to real JSON locations. Also used by `tools/check-edit-ids.mjs`. |
| `_github.js` | Commits files to the repo through the GitHub API, as one commit. Used only by `edit.js`. |

Several of these functions read `standalone/src/data/*.json` directly (`_order.js` and `checkout.js` read the catalogue and settings, `social.js` reads `pages/social.json`), so those data files are part of what the functions ship with.

Environment variables for these functions are listed in [`standalone/README.md`](standalone/README.md#environment-variables).

## How a change goes live

Vercel serves this repo as it is committed. It runs no build of its own, so the built shop has to be committed at the repo root. The "Build the shop" GitHub Action does that.

1. Create a branch and change files under `standalone/` (or `tools/`, or the workflow).
2. Open a pull request to `main`. On a pull request the Action installs, builds and runs every check, and runs `tools/publish.mjs` in its checkout, but it does not commit or push.
3. Merge to `main`. The push runs the Action again. If `standalone/**`, `tools/**` or `.github/workflows/build-shop.yml` changed, it builds `standalone/`, runs the checks, copies the build into the repo root with `tools/publish.mjs`, and commits any difference as "Rebuild the shop" by `blitzspirit-bot`.
4. Vercel deploys that commit as-is.

The Action can also be started by hand (`workflow_dispatch`).

The inline editor at `/edit` uses the same route. It commits JSON to `standalone/src/data/` on `main` through `api/edit.js`, the Action rebuilds, and Vercel deploys the rebuilt commit. That is why an edit does not show on the live site until the Action has finished.

`docs/DEPLOYMENT.md` describes this arrangement and is correct on the mechanism. Its last paragraph, which mentions the shop's "brief stay under `/new/`", is history: `vercel.json` still redirects `/new` and `/new/*` to the root, but nothing is served from `new/` any more.

### Consequences

- **Never hand-edit the built files at the repo root.** The next publish replaces every entry listed in `.published`, and your change is lost. Edit `standalone/` instead.
- **A green Action is not a live deploy.** The Action only proves the build and the checks passed and that the commit was pushed. Vercel deploys separately. After a merge, load the live page and confirm the content you changed is there, not just that it returns 200.
- **Only function source belongs in `api/`.** Vercel treats every file under `api/` as a build input, so a stray `.sql`, `.md` or other non-function file there can fail the whole deployment. The one exception to the naming pattern is the `_`-prefixed shared modules, which Vercel does not route.
- **Keep `vercel.json` to redirects.** `docs/DEPLOYMENT.md` records that unknown top-level keys are rejected and fail the deployment with an unhelpful error.
- **Do not add root-level files or directories named like a build output** (for example `products`, `cart`, `edit`). The publish step copies the build over whatever has that name. It only refuses, with an error, when the build wants to overwrite one of the source paths it knows about (`api`, `standalone`, `tools`, `docs`, `old`, `shopify-theme`, and the config files).
- **The Action commits to `main`.** Pull before you push to `main` if the Action has just run.
